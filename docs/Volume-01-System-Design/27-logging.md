# 27.1 Introduction

Every component of the Distributed Task Scheduler Platform continuously generates operational information.

Examples include:

- API requests
- Job scheduling
- Job promotion
- Worker execution
- Retry attempts
- Notification delivery
- Database operations
- Infrastructure events

Without centralized logging, investigating problems across multiple services becomes extremely difficult.

The platform therefore collects logs from every service into a centralized logging system where they can be searched, filtered, and correlated.

---

# 27.2 Why Centralized Logging?

Consider a job execution request.

```text
Client

↓

API

↓

Timer Service

↓

Scanner

↓

Dispatcher

↓

RabbitMQ

↓

Worker

↓

Notification Service
```

Every service generates its own logs.

Without centralized logging:

```text
API Server

↓

Local File
```

```text
Worker

↓

Another File
```

```text
Scanner

↓

Different Machine
```

Finding the complete execution history becomes extremely time-consuming.

Instead:

```text
All Services

↓

Centralized Logging

↓

Search Once
```

---

# 27.3 Design Goals

The logging system is designed to provide:

- Centralized log collection
- Structured log format
- Fast searching
- Correlation across services
- Long-term retention
- Low logging overhead
- Horizontal scalability
- Secure access

Logs support operational debugging rather than business history.

Business history is maintained by the Audit Service.

---

# 27.4 Logging Architecture

```text
           All Services

      ┌──────┼──────┐

      │      │      │

     API  Worker Scanner

      │      │      │

      └──────┼──────┘

             │

      Structured Logs

             │

       Log Collector

             │

            Loki

             │

          Grafana
```

Each service writes structured logs to standard output.

A log collector forwards logs into Loki.

Grafana provides searching and visualization.

# 27.5 Structured Logging

Logs are emitted as structured JSON instead of plain text.

Example:

```json
{
  "timestamp": "...",
  "level": "INFO",
  "service": "worker",
  "jobId": "job-248",
  "traceId": "trace-91",
  "message": "Job execution completed"
}
```

Common fields include:

| Field         | Purpose                    |
| ------------- | -------------------------- |
| timestamp     | Event time                 |
| level         | Severity                   |
| service       | Producing service          |
| instance      | Service instance           |
| traceId       | Distributed trace          |
| correlationId | Request identifier         |
| tenantId      | Tenant context             |
| jobId         | Related job                |
| message       | Human-readable description |

Structured logs are easier to search and analyze than plain text.

# 27.6 Log Levels

The platform uses standardized log levels.

| Level | Purpose                  |
| ----- | ------------------------ |
| TRACE | Detailed execution flow  |
| DEBUG | Development diagnostics  |
| INFO  | Normal operations        |
| WARN  | Recoverable issues       |
| ERROR | Failed operations        |
| FATAL | Critical system failures |

Example:

```text
INFO

↓

Job Scheduled
```

```text
WARN

↓

Retry Scheduled
```

```text
ERROR

↓

Worker Failed
```

Consistent log levels simplify monitoring and alerting.

# 27.7 Correlation IDs & Context Propagation

Every request receives a correlation identifier.

```text
API

↓

Correlation ID

↓

Timer Service

↓

Scanner

↓

Dispatcher

↓

Worker

↓

Notification
```

Every log generated during that request includes the same identifier.

Example:

```text
corr-72ab91
```

Trace identifiers generated by OpenTelemetry are also included.

Together they allow operators to reconstruct the complete lifecycle of a request across every service.

---

# 27.8 Log Aggregation

Logs from every service are collected automatically.

```text
Service

↓

stdout

↓

Collector

↓

Loki

↓

Grafana
```

The collector performs:

- Log collection
- Metadata enrichment
- Compression
- Forwarding
- Buffering during temporary outages

Services remain unaware of the storage backend.

# 27.10 Retention & Archival

Operational logs grow rapidly.

Typical retention:

| Age       | Storage                   |
| --------- | ------------------------- |
| 30 Days   | Loki                      |
| 90 Days   | Compressed Archive        |
| Long-Term | Object Storage (optional) |

Retention policies balance operational usefulness with storage costs.

Audit records remain available independently of log retention.

# 27.11 Failure Recovery

## Collector Failure

```text
Collector

↓

Restart

↓

Resume Collection
```

---

## Loki Failure

```text
Loki

↓

Unavailable

↓

Collector Buffers

↓

Reconnect

↓

Upload Logs
```

---

## Service Restart

```text
Service

↓

Restart

↓

Continue Logging
```

---

## Disk Failure

If local buffering is lost:

```text
Buffered Logs

↓

Lost
```

Business operations continue normally.

Logs are valuable for diagnostics but are not considered business-critical data.

---

# 27.12 Performance Optimization

## Asynchronous Logging

Application threads should not wait for remote log storage.

```text
Application

↓

Log Queue

↓

Collector
```

---

## Structured JSON

Machine-readable logs eliminate expensive text parsing.

---

## Log Sampling

High-frequency debug logs may be sampled.

Example:

```text
10,000 Events

↓

100 Logged
```

Sampling reduces storage costs while preserving operational insight.

---

## Log Rotation

Local buffers are automatically rotated to prevent excessive disk usage.

# 27.14 Logging Best Practices

The platform follows these principles:

- Use structured JSON logs.
- Include correlation and trace identifiers.
- Avoid logging sensitive information.
- Use consistent log levels.
- Keep log messages concise and meaningful.
- Never use logs as business storage.
- Centralize log collection.
- Rotate local buffers.
- Sample extremely high-volume logs.
- Monitor log ingestion health.
